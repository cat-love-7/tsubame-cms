# UI Localization (i18n)

**Status: implemented** (2026-09). The mechanism - Transloco 8, language resolution, switching UI, key-consistency tests,
error codes shown alongside - and **keying of every screen**, plus `Intl` date formats, are complete. What remains is content
localization (§4).
Descriptions from when work had not started are left as they are - back then wordings were hard-coded and English and Japanese were mixed together.

## 1. Decisions

| Item | Decision |
|---|---|
| Default language | **Prefer the browser's language settings** - match in the order of `navigator.languages` |
| Unsupported languages | Fall back to **English** |
| Switching | **Yes** - manual; a saved choice takes highest priority |
| Regional variants | **Make region-tagged values such as `ja-JP` / `en-GB` handleable in the future** - for now only the two, `ja` / `en`, need to be implemented, but write the resolution rules in a region-aware form |
| Server errors | **Show the code alongside**, and keep `message` **uniformly in English**. The display wording lives on the client |
| Content localization | **Not done this time** - recorded as a TODO in §4 |
| Missing keys | **Detected mechanically** (§3) |

### Resolution rules (written in anticipation of regions)

```
Saved choice (e.g. "ja") → walk navigator.languages in order:
  "ja-JP" → "ja" (drop the region) → adopt it if it is in the mapping table
  if no language matches, "en"
```

The implementation uses **a library that can switch at runtime**, not Angular's standard `$localize`
- the Angular standard splits builds per locale, so switching requires a reload.
Transloco is recommended - Angular native, signal support, ICU support.

## 2. Terminology decision list (translate / katakana / leave as is)

The premise is to **think of identifiers and labels separately**: field type names (`Text` / `Markdown` / `Number` …) and
permission JSON keys (`can_view` …) are **data, not display wording**, so they stay in English.
Only the **labels** shown on screen are subject to translation.

### 2.3 Things that must not be translated

- Field type names (`Text` / `Markdown` / `Number` / `Boolean` / `Date` / `DateTime` / `Image` /
  `CompositeField` / `Array` / `TextEnum`)
- Permission JSON keys, routes, query names (`limit` / `offset` / `status` …)
- `Tsubame` (product name), `ID` (the identifier itself), displays of identifiers such as `{{ id }}`
- **The deployment's own name** (`SITE_NAME`, drawn in the app bar, on the sign-in card and in the
  tab title). It is the operator's wording for one site, so there is nothing to translate it into:
  a catalog entry per language would be a place for the two to disagree about a name.
- Wordings that contain a status code in the sentence (such as `429`)

## 3. Mechanical checks on keys and codes

Translations inevitably go missing if left alone, so **fail them in tests**. The implementation is
`frontend/src/app/core/i18n/catalog.spec.ts` and `keys.spec.ts`.

1. **Correspondence between language files**: the key sets of `ja.json` and `en.json` must match (a missing key and an extra key both fail).
2. **Existence of the keys actually used**: scan the templates and TS for `… | transloco` / `t('…')` / `failure('…')`
   and verify they **exist in both language files** (`keys.spec.ts`). Even when the key sets match,
   a misspelling on the template side can only be found this way. This check actually found
   `auth.signInFailed` (it pointed at a non-existent key) and `content.failedToLoadComposite`
   (forgotten to add to the catalogue).
3. **Placeholder correspondence**: the `{{…}}` of the same key must be identical in both languages
   (it fails if a translation drops a value).
4. **Behaviour when a key is missing**: at runtime **fall back to English**, and **do not show the key string on screen**.
   Development builds emit a warning to the console.
5. **Server error codes**: write out the list of codes on the Rust side as `error-codes.json`
   (a Rust test verifies the match), and test that **the catalogue's `errors.*` covers every code**.
   Adding a code on only one side fails.
   - The server returns `{"code": "…", "message": "…"}`. `message` stays in English (for logs,
     curl, and existing tests); the client turns a known `code` into its own wording, and for an
     unknown one displays `message` as is (adding a new code does not break old clients).
   - Codes are published split into **two kinds**. **Situational codes** (such as `username_taken`) are
     the reason themselves, so they may be replaced with the client's wording. **Status codes**
     (such as `bad_request`) are not the reason - the same `bad_request` is attached to a missing
     field and to a duplicate name, so keep `message` (the only sentence saying which input is bad)
     and translate only the screen-specific prefix (`Save failed: …`). This distinction is
     distributed as `situational` / `status` in `error-codes.json`, and
     `failure()` (`message.ts`) uses them differently.

## 4. TODO: Content localization (a different scale from i18n)

**Out of scope this time.** This is about localizing not the UI wording but **the data authors write**, and it needs a separate design.
At minimum the following decisions are needed:

- Granularity: hold a language per field, or make a separate record per language per item
- The language axis of the public API (`?lang=` or `Accept-Language`) and the fallback rules for untranslated fields
- Editing flow: see all languages on one screen, or switch per language. How to represent a "waiting for translation" state
- URL strategy (a separate path per language, or resolving on the same path) and SEO
- Migration of existing data (which language to treat single-language content as)

## 5. Shape of the implementation (2026-09)

- Introduced **Transloco 8** (`@jsverse/transloco`). Catalogues **bundle** `assets/i18n/*.json`
  (`BundledTranslocoLoader`), so that reading a screen does not wait on HTTP.
- **Language resolution** (`core/i18n/language.ts`, a pure function + tests): saved value → `navigator.languages`
  (matched with the region dropped) → English. **If the saved value becomes an unsupported language, ignore it**
  and fall back to the browser (so the UI is not left on a deleted catalogue).
- **`LanguageService`**: saves the choice (`localStorage`), updates `<html lang>`, and reflects it into Transloco.
  The root component calls `initialize()` once at startup.
- Placed the **switching UI** (`LanguageSwitcher`) on the **sign-in screen** (because people who cannot read the
  language the browser guessed are exactly the people whose setting is hidden behind signing in).
- **Keyed the sign-in screen**. Errors were changed to the form of **key + parameters**
  (`auth.tooManyAttempts` + `{seconds: 600}`. Later consolidated into `MessagePipe`; see §3 and §5).
  English messages returned by the API are displayed as is (what a client that does not know the reason can honestly do).
- Tests: 5 for the resolution rules, 3 for catalogue consistency, and the sign-in English display and **switching to Japanese** (through to saving).

- **Error codes shown alongside**: the API returns `{"code": "…", "message": "…"}` (`message` stays in English,
  for logs, curl, and existing tests). The list published by `ERROR_CODES` (Rust) is copied into
  `frontend/src/assets/error-codes.json`, **a Rust test verifies the match**, and
  **a frontend test verifies that the catalogue's `errors.*` covers them all**. If the three drift apart, it fails.
  The client turns a known `code` into its own wording, and for an unknown one displays `message` as is
  (`errorKey` / `errorMessage` and their 5 tests). The point of this shape is that **an unknown code does not
  break old clients**.

- **Situation-specific codes**: added 9 in addition to the generic codes derived from status
  (`invalid_credentials` / `invalid_token` / `session_ended` / `account_disabled` /
  `not_provisioned` / `invalid_username` / `weak_password` / `username_taken` /
  `last_administrator`). **The wire format does not change**, so the rest is just adding
  `with_code(...)` at the call sites. Tests were changed to **verify by code**, not by wording
  (the wording may change, but the code is a contract the client depends on).

- **Fixing the language in tests and E2E**: component tests use `provideTestTransloco()` from
  `core/i18n/testing.ts` to get **the real catalogues + English** (a non-existent key fails, and they
  do not depend on the language of the execution environment. Only tests that look at switching call
  `use('ja')` themselves). E2E opens the page after injecting `localStorage['tsubame.language'] = 'en'`
  with `addInitScript` (without injecting it, the moment a screen is translated it fails on a browser
  in a Japanese environment).

- **Keying of every screen**: moved the wording of screens other than sign-in (collection list, item editing,
  single page, schema editing, composite fields, image library, account management, own password,
  password reset) into the catalogues. Material icon names (`add` / `delete` /
  `menu`, etc.) and field type names (`Text` / `Markdown` …) are **data**, so they stay in English.
- **Screen messages are held as "key + parameters"** (`core/i18n/message.ts`). If errors or
  save completions were held as **already-rendered strings**, then switching the language while they are
  displayed would leave just those in the old language. `MessagePipe` resolves them at render time and
  subscribes to `langChanges$` to prompt a re-render. Server errors go through
  `failure(screen key, error)` (the two kinds of codes in §3).
- **Placed the language switcher in the header as well** (every screen after sign-in). Together with the sign-in screen, that is 2 places.
- **Dates via `Intl`**: `formatDateTime(value, language)` (`core/i18n/date-format.ts`) uses
  `Intl.DateTimeFormat` to render `en` / `ja` differently. The Updated column of lists, image
  upload timestamps, and the expiry of preview URLs / reset URLs use this. The language is
  a signal on `LanguageService`, so switching it changes the table values along with it.
- **Catalogues are bundled** (as designed), so as keys grow the initial bundle grows too.
  Before i18n 486 kB → currently 503 kB (raw). Raised the warning threshold in `angular.json` from 500 kB →
  560 kB (the error threshold stays at 1 MB).
- **Shared test environment**: `providersFile` in `angular.json` reads `src/test-providers.ts`,
  so every spec gets the same catalogue (fixed to English). No longer need to write the same 3 lines in
  35 files, and a forgotten line no longer causes a `NullInjectorError`.

**Remaining**: content localization (§4). `Intl` **number** formats (currently dates only) and
region-tagged catalogues (`en-GB` / `ja-JP`) are not yet supported (only the resolution rules are prepared in advance).
