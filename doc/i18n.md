# UI の多言語化(i18n)

**状態: 未着手**(2026-09 に方針だけ決定)。いまは仕組みが無く、文言は直書きで英語と日本語が
混在している(`Email (任意)` と `Sign in to SL CMS` が同じ画面群に並んでいる)。

## 1. 決めたこと

| 項目 | 決定 |
|---|---|
| 既定の言語 | **ブラウザの言語設定を優先**(`navigator.languages` の順に照合) |
| 非対応言語 | **英語**にフォールバック |
| 切り替え | **あり**(手動。保存された選択が最優先) |
| 地域差 | `ja-JP` / `en-GB` のような**地域つきの値も将来扱えるようにする**(いまは `ja` / `en` の 2 つだけ実装してよいが、解決規則は地域対応の形で書く) |
| サーバーのエラー | **コードを併記**し、`message` は**英語に統一**。表示文言はクライアントが持つ |
| コンテンツの多言語化 | **今回はやらない**(§4 に TODO として記載) |
| キーの欠落 | **機械的に検出**(§3) |

### 解決規則(地域対応を見込んだ形)

```
保存された選択(例 "ja") → navigator.languages を順に:
  "ja-JP" → "ja"(地域を落とす)→ 対応表にあれば採用
  どの言語も一致しなければ "en"
```

実装は Angular 標準の `$localize` ではなく **実行時切り替えができるライブラリ**を使う
(Angular 標準は locale ごとにビルドを分ける方式で、切り替えに再読み込みが要る)。
Transloco を推奨(Angular ネイティブ、signal 対応、ICU 対応)。

## 2. 用語の決定リスト(訳すか / カタカナか / そのままか)

**識別子とラベルを分けて考える**のが前提: フィールド型名(`Text` / `Markdown` / `Number` …)や
権限の JSON キー(`can_view` …)は**データであって表示文言ではない**ので英語のまま。
画面に出す**ラベル**だけが翻訳対象。

### 2.2 一般的な UI ラベル(訳でほぼ決まり。判断は不要)

### 2.3 訳してはいけないもの

- フィールド型名(`Text` / `Markdown` / `Number` / `Boolean` / `Date` / `DateTime` / `Image` /
  `CompositeField` / `Array` / `TextEnum`)
- 権限の JSON キー、ルート、クエリ名(`limit` / `offset` / `status` …)
- `SL CMS`(製品名)、`ID`(識別子そのもの)、`{{ id }}` のような識別子の表示
- ステータスコードを文中に含む文言(`429` など)

## 3. キーとコードの機械的なチェック

翻訳は放っておくと必ず欠けるので、**テストで落とす**。

1. **言語ファイル間の対応**: `ja.json` と `en.json` のキー集合が一致すること(欠けも余りも失敗)。
2. **使われているキーの存在**: テンプレートと TS の `t('…')` / `*transloco` を走査し、
   **両方の言語ファイルに存在する**こと。片方にしか無いキーはここで落ちる。
3. **キー欠落時の挙動**: 実行時は**英語にフォールバック**し、**キー文字列は画面に出さない**。
   開発ビルドではコンソールに警告を出す。
4. **サーバーのエラーコード**: Rust 側のコード一覧を `error-codes.json` として書き出し
   (テストで生成・検証)、フロント側の TS の対応表(`Record<ErrorCode, string>`)が
   **その集合を過不足なく覆っている**ことをテストする。片側だけコードを足すと落ちる。
   - サーバーは `{"code": "…", "message": "…"}` を返す。`message` は英語のまま(ログ・
     curl・既存テストのため)、クライアントは既知の `code` を自前の文言に、未知なら
     `message` をそのまま表示する(新コードを足しても古いクライアントが壊れない)。

## 4. TODO: コンテンツの多言語化(i18n とは別規模)

**今回は対象外。** UI の文言ではなく**著者が書くデータ**を多言語にする話で、別の設計が要る。
少なくとも次の判断が必要:

- 粒度: フィールド単位で言語を持つか、アイテム単位で言語ごとに別レコードにするか
- 公開 API の言語軸(`?lang=` か `Accept-Language` か)と、未訳フィールドのフォールバック規則
- 編集フロー: 1 画面で全言語を見るか、言語ごとに切り替えるか。「翻訳待ち」の状態をどう表すか
- URL 戦略(言語ごとに別パスか、同じパスで解決するか)と SEO
- 既存データの移行(単一言語のコンテンツをどの言語として扱うか)

## 4.5 実装済み(2026-09)

- **Transloco 8**(`@jsverse/transloco`)を導入。カタログは `assets/i18n/*.json` を**バンドル**
  (`BundledTranslocoLoader`)。画面を読む前に HTTP を待たせないため。
- **言語の解決**(`core/i18n/language.ts`、純関数 + テスト):保存値 → `navigator.languages`
  (地域を落として照合)→ 英語。**保存値が非対応言語になったら無視**してブラウザに戻る
  (削除したカタログに UI を残さない)。
- **`LanguageService`**: 選択の保存(`localStorage`)、`<html lang>` の更新、Transloco への反映。
  ルートコンポーネントが起動時に 1 回 `initialize()` する。
- **切り替え UI**(`LanguageSwitcher`)を**ログイン画面**に配置(ブラウザが推測した言語を読めない
  人が、まさにサインインの向こうに設定を隠されている人なので)。
- **ログイン画面をキー化**。エラーは**キー + パラメータ**を持つ形にした
  (`auth.tooManyAttempts` + `{seconds: 600}`)。API が返す英語のメッセージはそのまま表示する
  (理由を知らないクライアントが正直にできること)。
- テスト: 解決規則 5 件、カタログ整合 3 件、ログインの英語表示と**日本語への切り替え**(保存まで)。

**残り**: 他の画面のキー化(約 119 文字列のうちログイン以外)、サーバーのエラーコード併記、
テスト/E2E の**言語固定**(E2E はブラウザ既定に従うため、将来の翻訳で不安定になりうる)、
`Intl` による日付書式。
