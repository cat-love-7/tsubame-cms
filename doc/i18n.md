# UI の多言語化(i18n)

**状態: 実装済み**(2026-09)。仕組み(Transloco 8、言語解決、切り替え UI、キー整合テスト、
エラーコード併記)と**全画面のキー化**、`Intl` の日付書式まで完了。残りはコンテンツの
多言語化(§4)。
未着手だったころの記述はそのまま残してある(当時は文言が直書きで英語と日本語が混在していた)。

## 1. 決めたこと

| 項目 | 決定 |
|---|---|
| 既定の言語 | **ブラウザの言語設定を優先**(`navigator.languages` の順に照合) |
| 非対応言語 | **英語**にフォールバック |
| 切り替え | **あり**(手動。保存された選択が最優先) |
| 地域差 | `ja-JP` / `en-GB` のような**地域つきの値も将来扱えるようにする**(いまは `ja` / `en` の 2 つだけ実装してよいが、解決規則は地域対応の形で書く) |
| サーバーのエラー | **コードを併記**し、`message` は**英語に統一**。表示文言はクライアントが持つ |
| コンテンツの多言語化 | **今回はやらない**(§4 に TODO として記載) |
| キーの欠落 | **機械的に検出**(§3) |

### 解決規則(地域対応を見込んだ形)

```
保存された選択(例 "ja") → navigator.languages を順に:
  "ja-JP" → "ja"(地域を落とす)→ 対応表にあれば採用
  どの言語も一致しなければ "en"
```

実装は Angular 標準の `$localize` ではなく **実行時切り替えができるライブラリ**を使う
(Angular 標準は locale ごとにビルドを分ける方式で、切り替えに再読み込みが要る)。
Transloco を推奨(Angular ネイティブ、signal 対応、ICU 対応)。

## 2. 用語の決定リスト(訳すか / カタカナか / そのままか)

**識別子とラベルを分けて考える**のが前提: フィールド型名(`Text` / `Markdown` / `Number` …)や
権限の JSON キー(`can_view` …)は**データであって表示文言ではない**ので英語のまま。
画面に出す**ラベル**だけが翻訳対象。

### 2.3 訳してはいけないもの

- フィールド型名(`Text` / `Markdown` / `Number` / `Boolean` / `Date` / `DateTime` / `Image` /
  `CompositeField` / `Array` / `TextEnum`)
- 権限の JSON キー、ルート、クエリ名(`limit` / `offset` / `status` …)
- `Tsubame`(製品名)、`ID`(識別子そのもの)、`{{ id }}` のような識別子の表示
- ステータスコードを文中に含む文言(`429` など)

## 3. キーとコードの機械的なチェック

翻訳は放っておくと必ず欠けるので、**テストで落とす**。実装は
`frontend/src/app/core/i18n/catalog.spec.ts` と `keys.spec.ts`。

1. **言語ファイル間の対応**: `ja.json` と `en.json` のキー集合が一致すること(欠けも余りも失敗)。
2. **使われているキーの存在**: テンプレートと TS の `… | transloco` / `t('…')` / `failure('…')`
   を走査し、**両方の言語ファイルに存在する**こと(`keys.spec.ts`)。キー集合が一致していても、
   テンプレート側の綴り間違いはこれでしか見つからない。実際にこの検査が
   `auth.signInFailed`(存在しないキーを指していた)と `content.failedToLoadComposite`
   (カタログへの追加忘れ)を見つけた。
3. **プレースホルダの一致**: 同じキーの `{{…}}` が両言語で同じであること
   (訳が値を落とすと落ちる)。
4. **キー欠落時の挙動**: 実行時は**英語にフォールバック**し、**キー文字列は画面に出さない**。
   開発ビルドではコンソールに警告を出す。
5. **サーバーのエラーコード**: Rust 側のコード一覧を `error-codes.json` として書き出し
   (Rust のテストが一致を検証)、**カタログの `errors.*` が全コードを覆っている**ことを
   テストする。片側だけコードを足すと落ちる。
   - サーバーは `{"code": "…", "message": "…"}` を返す。`message` は英語のまま(ログ・
     curl・既存テストのため)、クライアントは既知の `code` を自前の文言に、未知なら
     `message` をそのまま表示する(新コードを足しても古いクライアントが壊れない)。
   - コードは**2 種類**に分けて公開する。**状況コード**(`username_taken` など)は
     コード自体が理由なので、クライアントの文言で置き換えてよい。**ステータスコード**
     (`bad_request` など)は理由ではない — 欠けたフィールドにも重複した名前にも同じ
     `bad_request` が付くので、`message`(どの入力が悪いかを言っている唯一の文)を
     残し、画面固有の前置きだけを訳す(`Save failed: …`)。この区別は
     `error-codes.json` の `situational` / `status` として配られ、
     `failure()`(`message.ts`)が使い分ける。

## 4. TODO: コンテンツの多言語化(i18n とは別規模)

**今回は対象外。** UI の文言ではなく**著者が書くデータ**を多言語にする話で、別の設計が要る。
少なくとも次の判断が必要:

- 粒度: フィールド単位で言語を持つか、アイテム単位で言語ごとに別レコードにするか
- 公開 API の言語軸(`?lang=` か `Accept-Language` か)と、未訳フィールドのフォールバック規則
- 編集フロー: 1 画面で全言語を見るか、言語ごとに切り替えるか。「翻訳待ち」の状態をどう表すか
- URL 戦略(言語ごとに別パスか、同じパスで解決するか)と SEO
- 既存データの移行(単一言語のコンテンツをどの言語として扱うか)

## 4.5 実装済み(2026-09)

- **Transloco 8**(`@jsverse/transloco`)を導入。カタログは `assets/i18n/*.json` を**バンドル**
  (`BundledTranslocoLoader`)。画面を読む前に HTTP を待たせないため。
- **言語の解決**(`core/i18n/language.ts`、純関数 + テスト):保存値 → `navigator.languages`
  (地域を落として照合)→ 英語。**保存値が非対応言語になったら無視**してブラウザに戻る
  (削除したカタログに UI を残さない)。
- **`LanguageService`**: 選択の保存(`localStorage`)、`<html lang>` の更新、Transloco への反映。
  ルートコンポーネントが起動時に 1 回 `initialize()` する。
- **切り替え UI**(`LanguageSwitcher`)を**ログイン画面**に配置(ブラウザが推測した言語を読めない
  人が、まさにサインインの向こうに設定を隠されている人なので)。
- **ログイン画面をキー化**。エラーは**キー + パラメータ**を持つ形にした
  (`auth.tooManyAttempts` + `{seconds: 600}`。後に `MessagePipe` へ共通化、§3・§4.5 参照)。
  API が返す英語のメッセージはそのまま表示する(理由を知らないクライアントが正直にできること)。
- テスト: 解決規則 5 件、カタログ整合 3 件、ログインの英語表示と**日本語への切り替え**(保存まで)。

- **エラーコード併記**: API は `{"code": "…", "message": "…"}` を返す(`message` は英語のまま、
  ログと curl と既存テストのため)。`ERROR_CODES`(Rust)が公開する一覧を
  `frontend/src/assets/error-codes.json` に写し、**Rust のテストが一致を検証**、
  **フロントのテストがカタログの `errors.*` の網羅を検証**する。3 者がずれたら落ちる。
  クライアントは既知の `code` を自前の文言に、未知なら `message` をそのまま表示する
  (`errorKey` / `errorMessage` とそのテスト 5 件)。**未知のコードで古いクライアントが
  壊れない**のがこの形の要点。

- **状況固有のコード**: ステータス由来の汎用コードに加えて 9 件を付けた
  (`invalid_credentials` / `invalid_token` / `session_ended` / `account_disabled` /
  `not_provisioned` / `invalid_username` / `weak_password` / `username_taken` /
  `last_administrator`)。**通信形式は変わらない**ので、残りは呼び出し箇所に
  `with_code(...)` を足すだけ。テストは文言ではなく**コードで検証**する形に変えた
  (文言は変えてよいが、コードはクライアントが依存する契約)。

- **テストと E2E の言語固定**: コンポーネントテストは `core/i18n/testing.ts` の
  `provideTestTransloco()` で**実カタログ + 英語**にする(存在しないキーは失敗、実行環境の
  言語には依存しない。切り替えを見るテストだけが自分で `use('ja')` する)。E2E は
  `addInitScript` で `localStorage['sl_cms.language'] = 'en'` を仕込んでからページを開く
  (仕込まないと、画面を訳した瞬間に日本語環境のブラウザで落ちる)。

- **全画面のキー化**: ログイン以外の画面(コレクション一覧・アイテム編集・単一ページ・
  スキーマ編集・複合フィールド・画像ライブラリ・アカウント管理・自分のパスワード・
  パスワードリセット)の文言をカタログへ移した。Material のアイコン名(`add` / `delete` /
  `menu` など)とフィールド型名(`Text` / `Markdown` …)は**データ**なので英語のまま。
- **画面のメッセージは「キー + パラメータ」で持つ**(`core/i18n/message.ts`)。エラーや
  保存完了を**描画済みの文字列**で持つと、表示中に言語を切り替えたときそこだけ古い言語で
  残る。`MessagePipe` が描画時に引き、`langChanges$` を購読して再描画を促す。
  サーバーのエラーは `failure(画面のキー, エラー)` を通す(§3 の 2 種類のコードの使い分け)。
- **言語切り替えをヘッダーにも配置**(サインイン後の全画面)。ログイン画面と合わせて 2 か所。
- **`Intl` による日付**: `formatDateTime(value, language)`(`core/i18n/date-format.ts`)が
  `Intl.DateTimeFormat` で `en` / `ja` を出し分ける。一覧の Updated 列、画像の
  アップロード日時、プレビュー URL・リセット URL の有効期限がこれを使う。言語は
  `LanguageService` の signal なので、切り替えると表の値も一緒に変わる。
- **カタログはバンドル**(設計どおり)なので、キーが増えると初期バンドルも増える。
  i18n 前 486 kB → 現在 503 kB(生)。`angular.json` の警告しきい値を 500 kB →
  560 kB に上げた(エラーは 1 MB のまま)。
- **テスト環境の共通化**: `angular.json` の `providersFile` で `src/test-providers.ts` を
  読み、全スペックが同じカタログ(英語固定)を得る。35 ファイルに同じ 3 行を書く必要が
  なくなり、書き忘れによる `NullInjectorError` も起きない。

**残り**: コンテンツの多言語化(§4)。`Intl` の**数値**書式(いまは日付のみ)、
地域つきカタログ(`en-GB` / `ja-JP`)は未対応(解決規則だけ先に用意してある)。
